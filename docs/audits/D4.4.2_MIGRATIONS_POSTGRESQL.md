## D. Ledger e runner

Implementação em `runner.js:18` (carga/checksums), `runner.js:73` (DDL do ledger)
e `runner.js:87` (execução). O ledger contém:

| Campo | Contrato |
| --- | --- |
| `version` | INTEGER, PK, positivo, sequência 0001 em diante |
| `name` | TEXT, NOT NULL, UNIQUE |
| `checksum` | SHA-256 do SQL; CRLF normalizado para LF |
| `schema_checksum` | SHA-256 da representação JSON esperada |
| `runner_version` | INTEGER, versão 1 deste formato |
| `applied_at` | TIMESTAMPTZ, `clock_timestamp()` |

Um pool privado de tamanho 1 reserva um client. O advisory lock de sessão
`(1144270386,2)` é adquirido antes de inspecionar/criar ledger e cobre a execução
inteira. Cada migration usa **o mesmo client** para BEGIN, SQL, validação,
inserção do histórico e COMMIT. A primeira transação inclui o ledger.
Não há consultas DDL independentes ao pool global. A API pública F1 permanece
inalterada; o runner usa `pg` com a configuração e sanitização de erros da F1.

Checksums/nome alterados, versões incompatíveis e schema divergente causam
recusa. Segunda execução não altera definições, OIDs, timestamp nem xmin do
ledger. Falha intermediária desfaz DDL, extensões e fixtures; falha em versão
posterior mantém o prefixo previamente confirmado. Não há registro incompleto
de sucesso nem reparo automático de histórico.

Na interrupção, a sessão é destruída; PostgreSQL desfaz trabalho não confirmado
e libera o lock ao encerrar a sessão. Isso pode aguardar a instrução corrente
(observado com `pg_sleep`), não é cancelamento instantâneo. Prazos por operação:
conexão 5 s, statement/lock 15 s, leitura 17 s, transação ociosa 15 s.
Falha durante COMMIT marca resultado desconhecido; reexecução reconcilia pelo
ledger. Não foi simulada perda de resposta exatamente no COMMIT nesta entrega.

Todas as migrations F2 são transacionais. Operações como
`CREATE INDEX CONCURRENTLY` falham sem fallback para autocommit; suporte futuro
a operações não transacionais exige estratégia própria. As fontes SQL são código
confiável revisado e não podem conter comandos de controle transacional.

## E. Baseline versus legado

| Diferença | Justificativa e impacto |
| --- | --- |
| `case_questions.question_id`: SET NULL → RESTRICT e NOT NULL explícito | PK já proibia NULL. Agora a exclusão física é bloqueada por FK, preservando associação; não se escolheu exclusão em cascata. Soft delete permanece compatível. Nenhuma FK existente foi alterada |
| CHECK de role duplicado removido | Mesma expressão continua aplicada; nenhuma mudança de valores/RBAC |
| Trigger de cases declarado uma vez | O SQL original fazia CREATE OR REPLACE duas vezes; o objeto final é equivalente |
| `validated_by_id` direto no CREATE TABLE | Mesma definição/FK, outra posição ordinal. Importação futura deve usar nomes de colunas |
| `NOW()` versus `CURRENT_TIMESTAMP` | Mesma semântica temporal de transação, sem conversão de timezone |
| Estado final das migrations incorporado | Inclui local links, módulos, lifecycle, membership, identidade e traduções sem executar backfills |
| Seeds editoriais e upgrades removidos | Baseline exige banco vazio; não adota schema existente, inclusive fora de public |
| GIN/extensões preservados no PostgreSQL | PGlite retira extensões e substitui GIN no loader; o novo motor suporta e testa as definições SQL originais |

Não há migration de upgrade de bancos legados neste pacote. Ausência de ledger
com objetos existentes causa `F2_LEGACY_BASELINE_REFUSED`; nenhuma tabela é tomada
isoladamente como prova de schema completo. Upgrades e dados requerem inventário,
reconciliação e autorização próprios em fases futuras.

## G. Riscos e decisões pendentes

- O runner é deliberadamente test-only; não é ferramenta liberada para produção.
- Upgrades/adopção de bases legadas, dados e reconciliação não estão implementados.
- RESTRICT em case_questions é a decisão conservadora do baseline vazio;
  eventual política de exclusão física requer revisão explícita antes de migrar dados.
- O manifesto estrito cobre objetos da aplicação e extensões; não audita donos,
  comentários, grants, papéis operacionais ou alterações hostis do ledger por DBA.
- PostgreSQL major/extensões e alterações de deparse exigem revisar manifests.
- Papéis separados de DDL/runtime e TLS remoto não foram exercitados no F2 local.
- Não há DOWN destrutivo, retries cegos ou recuperação de dados de produção.
- Nenhum gate local solicitado ficou dependente de infraestrutura externa.
