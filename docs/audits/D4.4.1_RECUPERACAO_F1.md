# D4.4.1 — Recuperação e aceite local de F1

Verificação realizada em 2026-09-26. Os gates locais de F1 passaram sem alteração
da implementação. Isso não autoriza integração produtiva ou avanço para F2.

## A. Causa do exit 1 anterior

O arquivo `%TEMP%\D4.4.1-jest-full.log` foi lido integralmente para análise
(3.869 linhas). Resultado: **1 suite falhou, 93 passaram; 19 testes falharam,
788 passaram; 384,985 s**. A única suite com falha foi
`__tests__/postgresAdapter.integration.test.js`.

Todos os 19 testes receberam o mesmo erro no `beforeAll`, antes de criar fixtures:

```text
PostgresAdapterError: PostgreSQL timeout failure during connect
  classifyPostgresError (backend/database/postgres/errors.js:40:12)
  reserve (backend/database/postgres/index.js:70:13)
  executeQuery (backend/database/postgres/index.js:145:13)
  assertTestDatabase (__tests__/postgresAdapter.integration.test.js:45:22)
  beforeAll (__tests__/postgresAdapter.integration.test.js:84:24)
```

A conexão inicial para identificar o banco venceu o prazo configurado de
`DB_CONNECTION_TIMEOUT_MS=1000`. O hook compartilhado fez os 19 testes falharem;
o resultado não demonstra 19 defeitos independentes de pool/transação.
`errors.js` apenas classificou o timeout: não originou a falha.

O log não contém telemetria suficiente para determinar por que a conexão demorou.
Lentidão transitória do host/Docker é uma hipótese, não causa comprovada.
Não houve reprodução do timeout nas duas execuções atuais, com o mesmo código.
Não foi confirmada regressão de F1 ou configuração inválida. O runner anterior
verificava prontidão dentro do container via `pg_isready`; isso não mede o tempo
de autenticação pelo host. Não se alterou timeout nem se acrescentou retry para
ocultar o resultado histórico.

O 401 da sessão Codex é independente. Não é SQLSTATE de autenticação PostgreSQL.
O aviso experimental de VM Modules aparece também nas execuções aprovadas;
o PowerShell o apresenta como `NativeCommandError`, mas o exit real dessas
execuções foi zero. Os demais `console.error`/warnings do log pertencem a suites
aprovadas, incluindo cenários negativos esperados.

Nesta retomada, o Docker estava inicialmente parado. Após iniciá-lo, o sandbox
impediu acesso ao daemon; a tentativa focal no sandbox terminou em exit 1 com
`Local Docker command failed: run`, antes de executar Jest. A repetição autorizada
fora do sandbox passou. Essas ocorrências atuais não provam a causa do log antigo.

Log original preservado; SHA-256 antes e depois:
`598FF6E945785A582D938D2765776D2EF355B706D884815E9C429F8B82BE75DF`.
